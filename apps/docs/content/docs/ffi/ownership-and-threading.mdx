## Ownership

Every pointer the library hands you was allocated by Rust, so C's `free()` cannot release it. Each one has a matching free function. Borrowed pointers, such as the `ad_last_error_*` strings and entries returned by `*_list_get`, are never freed.

- Every free function accepts null and does nothing.
- Freeing a list handle or an image buffer twice is undefined behavior. Set the pointer to `NULL` after you free it.
- `ad_free_handle` zeroes the handle, so a second call on the same struct is a no-op. Free handles before you destroy the adapter that produced them.
- Strings inside a struct belong to the struct's owner. Do not free them one by one.
- Every fallible function zeroes its out-parameter before validating anything, so calling the paired free function after a failure is safe.
- `ad_resolve_element_exact` and `ad_execute_ref_action_exact_with_policy` allocate nothing. They fail with `AD_RESULT_ERR_ACTION_NOT_SUPPORTED` and leave their out-parameter null or zeroed.

## Threading

Entrypoints may be called from any host thread. Native handles are the exception: resolve, use, and release a handle on the same thread, with the adapter that produced it; anything else returns `AD_RESULT_ERR_INVALID_ARGS`. To pass a target across threads, pass the qualified ref and use `ad_execute_by_ref`.

<table>
  <thead>
    <tr><th>Concurrent calls</th><th>Contract</th></tr>
  </thead>
  <tbody>
    <tr><td>read and read</td><td>Both run concurrently.</td></tr>
    <tr><td>read and mutation</td><td>The read does not wait and may overlap the mutation; its result is a point-in-time observation.</td></tr>
    <tr><td>mutation and mutation</td><td>Different applications run together. The same application, and any machine-wide mutation (no target, shared pointer or keyboard, or focus steal), has one holder at a time for the same OS user. A waiter that cannot get the lock returns a structured timeout.</td></tr>
  </tbody>
</table>

Snapshots, finds, listings, screenshots, clipboard reads, status, and trace reads are observations. Ref actions, native-handle actions, input synthesis, clipboard writes, app and window changes, and notification actions are mutations. The locks are shared with the CLI. Headless actions on different applications run together. The same application, and every machine-wide mutation, runs one at a time across threads and processes of one user. A lock covers one command, not a transaction: the UI can change between an observation and a later action.

- `ad_adapter_destroy` revokes the adapter. Calls already in flight finish; calls that start afterward return `AD_RESULT_ERR_INVALID_ARGS`.
- `ad_wait` blocks its calling thread for at most `scope.timeout_ms`.
- The `ad_set_log_callback` callback may run on any thread that calls an `ad_*` function, concurrently, and may still fire briefly after you unregister it. Keep it alive for the process lifetime and never let it unwind across the C ABI.
- A language runtime's global lock does not give thread affinity; keep native handles in thread-confined objects, or use refs.
- On macOS, `ad_check_permissions` reports Accessibility trust for the host executable (`python3`, `node`, your app), not for the library.

## Errors

A failing `AdResult` function returns a negative code and fills the calling thread's last-error slot. Read it before the next call that can fail.

```c
AdExactWindowInfo win = {0};
AdResult rc = ad_launch_app_exact(adapter, "gnome-calculator", 5000, &win);
if (rc != AD_RESULT_OK) {
    const char *msg = ad_last_error_message();
    const char *sug = ad_last_error_suggestion();   /* may be NULL */
    fprintf(stderr, "launch failed (%d): %s\n", (int)rc, msg ? msg : "(no message)");
    if (sug) fprintf(stderr, "  suggestion: %s\n", sug);
    return -1;
}
ad_release_exact_window_fields(&win);
```

The strings stay valid across later successful calls on the same thread; only the next failing call replaces them, like POSIX `errno`. The slot is thread-local. Retry only when the retry disposition is `AD_RETRY_DISPOSITION_SAFE`, as described in [Errors and recovery](/desktop/errors-and-recovery#disposition).

`AdResult` codes mirror the CLI's [error codes](/desktop/errors-and-recovery#error-codes): `AD_RESULT_ERR_PERM_DENIED` is -1 through `AD_RESULT_ERR_APP_UNRESPONSIVE` at -16. The full list is on the [API page](/desktop/ffi/api#enums). Treat any negative value outside that list as an unknown error, because new codes can be appended.

### Two failure modes for JSON entrypoints

The JSON entrypoints fail in two ways, so check `*out` before you decide whether to free:

- **Argument or infrastructure failure** (a null adapter, bad UTF-8, a bad enum): `*out` is null, nothing is allocated, and only the last-error slot reports it.
- **Command failure** (app not found, `STALE_REF`, `TIMEOUT`): `*out` holds an `"ok": false` envelope that you free with `ad_free_string`. The last-error slot is also set.

### Refs, enums, and panics

Ref-taking functions accept only `@<snapshot_id>:e<N>`. A bare or malformed ref returns `AD_RESULT_ERR_INVALID_ARGS` before dispatch; a missing snapshot returns `AD_RESULT_ERR_SNAPSHOT_NOT_FOUND`; a missing ref returns `AD_RESULT_ERR_STALE_REF`. Every `int32_t` enum field is validated, so an out-of-range value returns `AD_RESULT_ERR_INVALID_ARGS` instead of undefined behavior. Every entrypoint traps panics and reports them as `AD_RESULT_ERR_INTERNAL`, but only in a library built with the `release-ffi` profile; see [Build and link](/desktop/ffi/build-and-link#build-from-source).
